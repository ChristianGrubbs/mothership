# Global Signal ticker

Approved 2026-09-07. The shared admin layout renders a 34px announcement strip below the menu bar on every Mothership page for an account that has the alerts on (see Per-account setting). The existing authenticated Home RSS proxy serves feed data; no model/API classification or new application service is involved.

## Behavior

- Reads only designated OpenAI, Google, Anthropic, Higgsfield and thsottiaux feed names. URLs must match the designated provider domain (or its existing Google News wrapper); Sottiaux links must be his own X status URLs.
- Announcement headlines use explicit launch/model/reset rules. This is heuristic filtering, not an exhaustive classifier. General press feeds, personal X posts, tutorials, rankings, pricing and subscription promotions are excluded.
- The strip shows one headline below 900px, two from 900px, and three from 1400px, adjusting immediately on resize. It rotates every eight seconds, pauses on hover/focus, and respects reduced motion. There is no Pause button. Clicks open the original story in a new tab.
- Bell and brief popups report newly observed model releases and reset announcements once. First successful load silently baselines existing history. Later backfills predating that baseline never alert. Releases discovered after an outage still alert within seven days when published after the initial baseline.
- Cached stories, unread alerts and deduplication are stored per account in this browser. Mark all read clears the badge. Navigation retains state. The ticker binds after initial Vue mount and after every AJAX navigation success, cleaning up old timers, requests and listeners before navigation. Browser Web Locks serialize checks across tabs where supported; storage events update badges without repeating popups.
- Reads the cached announcement endpoint at most every five minutes while visible, retains cached headlines offline, and stops requests in hidden pages. These are announcement alerts while Mothership is open, not personal account reset timers or operating-system notifications.

## Per-account setting

The strip and its **Announcement alerts** bell are a per-account choice (2026-10-23). **My Account > AI announcements** saves `admins.signal_alerts`, a nullable boolean on the signed-in account only; the page, the account API and the users screen never write another account's value. The layout asks `Mothership\DAM\Services\SignalAlerts` and still asks `HomeWidgetRegistry::permits('rss')`, so a role without the RSS tool gets neither the strip nor the switch. When the answer is no, the layout renders no strip markup and requests neither `ticker.css` nor `ticker.js`, so nothing fetches or polls the announcement endpoint. The choice applies from the next full page load, so other tabs that are already open adopt it when they next reload or open a normal admin page. Turning it off leaves the browser's saved read/unread history alone and turning it on again restores it. The operational notification bell and the Signal Home widget are separate and unaffected.

- **Explicit choice wins.** Saved `true` or `false` always overrides the fallback, including for the exception accounts.
- **Fallback (value NULL, never chose).** Off, unless the account matches an entry of `dam-home.signal_default_on` (`packages/Mothership/DAM/src/Config/home.php`) on its numeric id **and** its email (trimmed, case-insensitive). The shipped entry is id 1 `admin@mothership.local` (the example/demo account); more come from `MOTHERSHIP_SIGNAL_DEFAULT_ON`, a comma-separated list of `id:email` pairs. A reused id with another email, or the email under another id, stays off. New accounts start NULL, so they are off; no existing row was updated.
- **Requests that omit the field** (older clients, a role with no switch) leave the saved choice unchanged; a present value must be a boolean.
- **Tests and demos** that need the strip opt in explicitly (`signal_alerts` true on a fixture account) rather than relying on the exception list.

### Rollback to the earlier behaviour (strip on for every account whose role has the RSS tool)

## Sources

The existing Umbrel adapter (the URL set in `MOTHERSHIP_HOME_RSS_API`, ending in `/mothership-api`; there is no built-in address, and unset leaves the Signal and Trending widgets in their unavailable state) now exposes `/v1/announcements`. Its background collector checks six direct sources every 15 minutes, independently of browser tabs:

- OpenAI: official `https://openai.com/news/rss.xml` (full feed, no 100-item query cutoff).
- Google AI: official `https://blog.google/technology/ai/rss/`.
- Google DeepMind: official `https://deepmind.google/blog/rss.xml`.
- Anthropic: dated structured records from `https://www.anthropic.com/news`, including featured release landing pages outside `/news/` such as Fable 5.1.
- Higgsfield: official `https://higgsfield.ai/blog/rss.xml` (since 2026-10-17). It replaced the scrape of dated CMS records in `https://higgsfield.ai/blog`, which returned nothing after the blog's SolidStart rebuild (last success 2026-10-14).
- Tibo (thsottiaux): Codex reset posts via self-hosted RSSHub at `<SIGNAL_RSSHUB_URL>/twitter/user/thsottiaux` (the adapter's `SIGNAL_RSSHUB_URL` setting; there is no built-in address, and unset makes this one source report "Source address is not set"), parsed by the same standard RSS reader as the official feeds.

Google News subscriptions remain available in the normal RSS reader, but the ticker no longer relies on their incomplete indexing. The collector uses Python standard library only, with no paid API/model calls. Cached stories and per-source check/success timestamps persist in Docker volume `mothership-rss-state`. A failure retains that source's cached stories and does not block other sources. Empty/invalid parsers are errors. Checks older than 30 minutes are stale. The Sources control shows the healthy/total count and opens per-source status; transport failures show Sources offline. Each source in `/v1/announcements` also carries `error`, the short failure message (never a body), so an empty feed reads differently from an HTTP 403. This detects collection failures, not every possible editorial omission or upstream delay.

**Source alerts (2026-11-03).** The strip's "Sources 5/6" went unnoticed for days four times (Anthropic 2026-09-22, DeepMind 2026-09-28, Higgsfield 2026-10-17, Tibo 2026-10-28 to 2026-11-03). The collector now pushes an ntfy alert when a source has had no success for `SIGNAL_ALERT_AFTER_HOURS` (default 6), repeats it daily while the source stays down, and sends one recovery notice. The alert carries the error message, the healthy count, and a fix hint where one is known (Tibo: refresh the X cookie). ntfy settings come from `alerts.env` beside `deploy.py` on the adapter host (`NTFY_URL`, `NTFY_TOPIC`, `NTFY_USER`, `NTFY_PASS`). The same file holds `SIGNAL_RSSHUB_URL` and the optional `SIGNAL_RSSHUB_HINT`, a sentence appended to the X source's alert (for example the command that stores a new cookie on that host). That file never enters the repository, and without the ntfy keys alerts are off. An alert only reaches someone who is subscribed to that topic.

**Source fragility review (2026-11-03).** Four sources are official feeds: OpenAI, Google AI, Google DeepMind and Higgsfield. Anthropic is still a page scrape because it publishes no feed: `/rss.xml`, `/news/rss.xml`, `/feed` and `/news/feed.xml` return 404, and `/news` links none. Tibo is the most fragile source. It is an X account read through RSSHub with the `auth_token` cookie of an X account kept for that purpose, and X can revoke that cookie at any time; it did on 2026-10-28 01:39Z. An individual's X account has no official feed. Two things show the revocation: the Redis key `twitter:cookie:<token>` holds an `auth_token` with a 1970 expiry, and RSSHub logs `Twitter API error: 403` on every X route. Fix it by storing a new `auth_token` in RSSHub's configuration on its host.

Codex reset coverage went live on 2026-09-10, ending the 2026-09-07 deferral early. The blocker was that the paid ScrapeCreators probe returned popular rather than latest posts, which does not establish a chronological feed; self-hosted RSSHub on the adapter host (installed 2026-09-09) returns a chronological feed for free, so no paid polling is installed. RSSHub listens on the private network only and deliberately has no public hostname or DNS record. The collector reaches it server-side from inside `mothership-rss-api` on the same host, so remote visibility through the public application is unaffected, exactly as for the other five sources. An RSSHub outage marks only that source error or stale and retains its cached posts.

Alert rules, as of 2026-09-10:

- A model alert requires a version attached to the product name. After `ChatGPT` that version must be hyphen-attached or decimal, because a loose integer there is nearly always a count or duration: `ChatGPT Images 2.5`, `ChatGPT 5.5`, `ChatGPT-6` and `gpt-image-2.5` alert, while `Introducing projects in ChatGPT`, `ChatGPT 3 ways to organize your work`, `ChatGPT Images 4 ways to create faster` and `ChatGPT 5-day weather forecasts` stay plain headlines. `GPT-6` keeps the plain digit form the official feeds have always used.
- Because Sottiaux stories are already restricted to his own status URLs, any reset wording in his posts counts as a reset alert, including bare posts such as `All reset for everyone.` Negations before the word are excluded, matching `never`, `cannot`, `nothing` and any `n't` contraction with a straight or curly apostrophe — feed text uses curly ones.
- Negation is deliberately **not** matched after the word. The live post `banked resets not fully applying when used in ChatGPT Work and Codex` is a genuine reset announcement whose `not` qualifies the application, not the reset; suppressing it would lose a real alert. The accepted cost is that a phrasing such as `Reset will not happen today` still alerts.

## Umbrel deployment

Source is tracked in `tools/rss/`. Copy `server.py`, `announcements.py`, `trending.py`, `Dockerfile`, and `deploy.py` to the adapter directory on the Umbrel, written `<adapter-dir>` below (the Dockerfile builds all three Python files; leaving `trending.py` out is how the Umbrel drifted behind `main` until 2026-11-03), then run `python3 <adapter-dir>/deploy.py`. This preserves the running adapter's environment, mounts, network and restart policy in memory, adds its persistent cache volume, and retains the previous stopped container for rollback. Replaying mounts skips the `mothership-rss-state` volume that the script adds itself, so a redeploy over a container it previously created succeeds; any other non-bind mount still fails closed. Exactly one `mothership-rss-api-previous` container may exist, so remove the prior one before redeploying. It does not write FreshRSS data. Build success is required before replacing the adapter. Verify `/health` and `/v1/announcements`, including source success timestamps and the Fable 5.1 story, before deploying the ticker UI. `deploy.py` passes `alerts.env` as `--env-file` when it exists and does not replay that file's keys from the old container, so editing `alerts.env` and redeploying takes effect. Before the first deploy of a build that reads `SIGNAL_RSSHUB_URL` (2026-11-18 onward), add that key to `alerts.env`; a container built before then carries the address in its code and keeps working until it is replaced.

The public path runs through nginx in `freshrss-cloudflare-proxy`, whose config is a read-only bind of `default.conf` from that proxy's directory on the host. Its tracked copy is `tools/rss/freshrss-proxy.conf`. Since 2026-11-03 it resolves `mothership-rss-api` per request through Docker's DNS (`resolver 127.0.0.11`), so a redeploy no longer leaves `/mothership-api/` at 502 until `nginx -s reload`. Install changes to it with `nginx -t` and then `nginx -s reload` inside the container.

### Cold start (container missing)

`deploy.py` cannot cold-start: it inspects the running `mothership-rss-api` container to replay its env, mounts, network and restart policy. After the Umbrel reboot on 2026-09-25 that container and the RSSHub containers were absent from `docker ps -a`, while the images, the `mothership-rss-state` volume and the adapter directory survived. Recreate RSSHub first (its `.env` survives on disk), then the adapter with the command below (verified 2026-09-25 with literal host paths and without `--env-file`; the placeholders and `--env-file`, which supplies `SIGNAL_RSSHUB_URL` and the ntfy keys, were written in on 2026-11-18 and that form has not been run). The bind mount must target the `db.sqlite` file, not the `users/admin` directory: the image runs as the non-root `app` user, which cannot traverse that directory (`PermissionError` on `/data/db.sqlite`). `ALLOWED_ORIGINS` must include the live app origin `https://mothership.example.com`; the code default lists only the local preview origins plus `MOTHERSHIP_ASSETS_ORIGIN` when that is set. No `MOTHERSHIP_RSS_TOKEN` is needed for the browser widget. Afterwards, `<MOTHERSHIP_HOME_RSS_API>/health` must return 200 and `/v1/announcements` must show six sources with `lastSuccessAt == checkedAt`.

```bash
cd <rsshub-dir> && docker compose up -d
docker run -d --name mothership-rss-api --network umbrel_main_network --restart unless-stopped --env ALLOWED_ORIGINS=https://mothership.example.com,https://assets.example.org,http://localhost:4173,http://localhost:8080,null --env-file <adapter-dir>/alerts.env --mount type=bind,src=<freshrss-data>/users/admin/db.sqlite,dst=/data/db.sqlite,readonly --mount type=volume,src=mothership-rss-state,dst=/state mothership-rss-api:signal-v2
```
