# Relationships and compound files

## Before you begin
Open **DAM > Assets**, select an asset, and open **Edit Asset**. The **Relationships** and **Files** tabs appear only when your role has the corresponding permissions and you can access the asset.

A relationship is typed and directed. **Outgoing relationships** start at the asset you are viewing and point to another asset; **Incoming relationships** start at another asset and point to the current one. The type describes the connection. You can choose a suggested type such as `related-to`, `uses-texture`, or `derived-from`, or enter a free-form **Custom type**. A custom type must contain nonblank text and can be at most 64 characters.

## Steps
1. Open the first test asset's **Relationships** tab. Under **Add relationship**, choose a **Relationship type**, or choose **Custom type...** and enter a nonblank type. Select **Choose an asset**, pick the second test asset, and select **Add relationship**. Saving checks access to both the current asset and the target; an inaccessible target cannot be linked even if its asset ID is known.
2. Confirm the new row appears under **Outgoing relationships** on the first asset. Open the second asset and confirm the same connection appears under **Incoming relationships**, grouped under the same type.
3. Select **Remove relationship** on either asset. Reopen both assets and confirm each asset still exists and can still be opened. Removing a relationship deletes only that connection; it does not delete either related asset or its files.
4. Open **Files**. A capture group presents one member as **Primary** while keeping its companion asset records and original files. Each capture member has **Open** and **Download** actions. If management controls are available, **Make primary** changes which member represents the capture, and **Ungroup files** makes the members separate without deleting them.
5. In the attached-files table, use **Role** to understand each file's purpose, such as `original`, `sidecar`, `subtitle`, `proxy`, or `texture`. The table lists each file's current state only; when content is replaced, the earlier state is kept as a revision in history rather than shown as another file. **Open** serves that attachment when its format can be viewed, while **Download** requests it as a download. These attachment roles are separate from the capture group's **Primary** member designation, and access is checked against the asset that owns the file.
6. To group related files under this one Library entry, use **Stack** at the top of **Files**. Choose what the files have in common under **Grouped by** (**Product**, **Campaign**, **Use case** or **Other**), enter its name, such as a product name or SKU, a campaign name, or a use case, and select **Save stack**. A stack needs a name. To turn the stack back into a plain asset, choose **Not a stack** and save. Only people who can edit the asset see these controls; everyone else sees the stack's grouping and name.
7. To choose which file stands for the entry, select **Make representative** on that file's row. The file marked **Representative** is the one the Library card, preview and default download use. The two files swap roles and places: the previous representative keeps the role the promoted file had (for example **Alternate format**) and its own history. The entry's name takes the new file's extension, the page reloads, and the thumbnail and details follow the new file. A **Proxy** or **Thumbnail** is a preview of the representative, so it cannot become one.
8. To rename a file or change its role, select **Edit**, change **Role** or the label, and select **Save** (or press Enter; Escape cancels). The representative's role cannot be changed here; make another file representative instead. Use the up and down arrows to change the order of the files; the order is saved at once and kept after a reload.
9. When an entry holds more than one file, its preview shows the files in a strip under the image, each with a small picture where the file type has one (a 3D model in GLB, 3MF or STL format shows a cube badge and its type until someone who can edit the entry has opened it in the preview once; from then on it shows the picture the preview took of it, for every entry that holds the same file). Click a file, or press Enter on it, to see it in the preview; the arrow buttons and keys step through the files and stop at the first and last. Tick the box on a file (or press Space on it) to pick it for download, then choose **Download selected** to get the picked files as one zip, or choose **Download all** for every current file; earlier revisions are never included, and files with the same name are numbered. If you can edit the asset, drag a file, or press Alt+Left or Alt+Right, to change the order; it is saved at once. On the Library, a stack's card opens its main file in the preview when you click it, as any other card does; the strip under the image holds the stack's other files. To see the stack's files fanned out first, click the number on the card (in the list view, the number beside the name) and choose one; **Open main file** in the opened stack and in the right-click menu opens the cover in the preview.
10. To see a file's earlier versions, select **History** on its row. Each revision shows its number, when it was made, who made it (**System** when no person did), its size, checksum and any note, with **Download** for that version; the one marked **Current** is in use. If you can edit the asset, select **Restore** on an earlier revision to make it current again. Restoring adds a new revision with the note *Restored revision N* and keeps every earlier one, so nothing is lost. Restoring the representative file changes the entry's content like a re-upload: the page reloads, and the thumbnail and details follow.
11. A file that The Mothership made from the entry, such as an optimized or vectorized copy or a video preview, says under its label what made it and from which revision, for example *Made by Optimize from revision 1*. It keeps naming that revision after a newer upload. An entry saved from the image editor as a new asset says which entry it was made from, with a link back.

12. Below the asset's tabs, **Related** suggests up to eight other assets you can open, found from what they have in common with this one: shared tags (a rarer tag counts for more), the same stack name, a similar file name, a similar look when AI search is on, the same detail value such as a sponsor, and the same folder. Each card says why it is suggested, for example *same campaign · 1 shared tag*. The list is worked out each time it is shown and is never saved as a relationship. It leaves out this asset, the files in its stack and the assets it already has a relationship with, so it adds to the **Relationships** and **Files** tabs rather than repeating them. When nothing is in common, it says **No related assets yet.**

## Expected result
The relationship is shown as outgoing from its source and incoming to its target. After you remove it, the relationship row disappears in both directions while both assets and their files remain. The **Files** tab identifies capture members, file roles and the representative file, and provides the download actions allowed for your account. Changes to the representative, labels, roles and order are kept after a reload. A zip download holds only the entry's current files and only when you can view the entry. A file's history lists every revision, newest first, and a restore appears as its newest revision.

## Troubleshooting
An asset cannot link to itself. The same source, target, and type cannot be added twice; choose a different meaningful type only when it represents a genuinely different connection. A blank custom type is rejected. If adding, listing, or removing a relationship is forbidden, confirm that you can access both endpoint assets and that your role includes the required relationship action. Restricted opposite assets are omitted from incoming and outgoing results.

**Related** only ever suggests assets you can open, and the files you can't open don't change its order. Trashed files and files that aren't available yet or any more are never suggested. If a suggestion seems missing, it may be outside your folder access, already in a relationship with this asset, or in the same stack.

Relationship results are paged independently, with up to 25 outgoing and 25 incoming connections in one response. The relationship list endpoint uses `outgoing_page` for the outgoing direction and `incoming_page` for the incoming direction; advancing one does not advance the other. The current **Relationships** tab does not expose next or previous page controls and requests the first page of each direction, so ask an administrator or integration operator for help when a direction has more than 25 available connections.

If a capture companion or attachment is missing, it may be outside your folder access, the capture may have been ungrouped, or the attachment may no longer exist in storage. A failed **Download** does not remove the file record. A file that the version history or a generated output still points at cannot be removed; earlier versions stay in **History**. A former representative that has earlier revisions is kept for the same reason. **Restore** says a revision is already the current file when it, or a revision with the same content, is the one in use. Older entries may show **System** as the author of revisions made before authors were recorded. Vectorized copies made before lineage was recorded show no *Made by* line. If the source entry of an image editor copy is in a folder you cannot open, the copy says only that it was made from an entry you can't open. If saving the file order says the list changed since it was loaded, someone else changed the files; reload the page and try again. Ask an administrator to verify your folder grant, capture grouping, and file availability.
